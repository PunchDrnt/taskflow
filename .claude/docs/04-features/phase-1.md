# Phase 1 — แกนหลัก `v1.0.0`

> [← Feature Specifications](./README.md) · [ลำดับและ priority](../03-roadmap.md)

Phase 1 ยังไม่ปล่อยให้คนใช้จริง — เส้นนั้นอยู่ท้าย [Phase 3](./phase-3.md)
สิ่งที่ต้องได้จาก phase นี้คือแกนที่ทุก phase ถัดไปต่อยอด: ตัวตน · องค์กร · โปรเจกต์ · งาน

## Auth & Users

- Login / Logout (JWT + refresh token rotation — ดูรายละเอียดใน [`01-architecture.md`](../01-architecture.md#auth))
- **ล็อกอินด้วยอีเมลหรือ username ก็ได้** — ช่องเดียว ระบบดูจากรูปร่างเอง
- **`username`** ตัวล็อกอินที่ unique · **คนละอย่างกับชื่อเล่น** ([ตารางเทียบ](../02-database/schema.md#schema-iam))
- เบอร์โทร — ข้อมูลโปรไฟล์ · unique แต่ไม่บังคับกรอก · ไม่ใช่ตัวยืนยันตัวตน (2FA เป็น TOTP)
- **Remember me** — เป็นค่าของ `sessions.expires_at` ไม่ใช่กลไกใหม่ (ไม่ติ๊ก = สั้น, ติ๊ก = 15 วัน)
- ลืมรหัสผ่าน — ลิงก์ทางอีเมล **อายุ 30 นาที ใช้ได้ครั้งเดียว**
- เปลี่ยนรหัสผ่าน (ต้องใส่รหัสเดิม)
- โปรไฟล์: ชื่อจริง, **ชื่อเล่น**, username, เบอร์โทร, อีเมล, รูป
- **ล็อกบัญชีเมื่อใส่รหัสผิดหลายครั้ง**
- **2FA แบบ TOTP — เปิดเอง ไม่บังคับใคร** ([กลไกเต็ม](../01-architecture.md#two-factor-totp))
  · roadmap เขียนไว้ว่าเป็น Phase หลังและบังคับเฉพาะ system role · ลงครึ่งแรกก่อนเพราะการบังคับต้องมี system role ให้บังคับ ซึ่ง `iam.user_roles` ยังว่างอยู่

> ชื่อเล่นจำเป็น — คนไทยเรียกชื่อเล่นเป็นหลัก ค้นด้วยชื่อจริงอย่างเดียวจะหาไม่เจอ

**อายุลิงก์ reset 30 นาที** — เก็บเป็น env var ไม่ hardcode · token ใช้ได้ครั้งเดียว (`used_at`)
ซึ่งเป็นตัวกันความเสี่ยงจริง ความยาวของหน้าต่างเวลาเป็นตัวรอง · 10 นาทีสั้นเกินไปสำหรับคนที่
เช็คเมลบนมือถือระหว่างประชุม แล้วจะกลายเป็นการขอลิงก์ใหม่ซ้ำๆ ซึ่งไม่ได้ปลอดภัยขึ้น

**ล็อกเมื่อ login ผิดหลายครั้ง**

- นับที่ `iam.users.failed_login_attempts` · ปลดล็อกด้วย `locked_until`
  — เก็บใน DB ไม่ใช่ในหน่วยความจำ เพราะตัวนับที่รีสตาร์ทแล้วหายคือตัวนับที่คนโจมตีรีเซ็ตได้เอง
- **บอกว่าถูกล็อก แต่ไม่บอกว่านานแค่ไหน**
- **ลองผิดระหว่างที่ล็อกอยู่ ไม่ต่อเวลาล็อก** — ไม่งั้นใครก็ล็อกเพื่อนร่วมงานค้างไว้ตลอดกาลได้
- อีเมลที่ไม่มีในระบบ ไม่นับอะไรเลย — ไม่มีอะไรให้ล็อก และการทำเป็นล็อกจะเผยว่าอีเมลไหนมีอยู่

**ไม่มี public register ใน Phase 1** — endpoint `/register` มีอยู่ แต่ดักด้วย `FeatureService.isEnabled(org, 'public_registration')` ซึ่ง return `false` ตั้งแต่บรรทัดแรก

> ถ้าเปิดสมัครเสรี ใครที่รู้ URL ก็สมัครเข้ามาแล้วรอให้ใครสักคนเผลอเพิ่มเข้า org
>
> นี่เป็นการใช้งานจริงครั้งแรกของ `FeatureService` — ไม่ต้องรอ Phase 7

**สร้าง user ช่วงแรก:** ยิง admin API ด้วย Postman หรือ seed script · หน้าจอเชิญคนมา Phase 2

**Email unique ระดับทั้งระบบ** — 1 อีเมล = 1 account แล้วคนนั้นเข้าได้หลาย org ผ่าน `organization.members`

```sql
CREATE UNIQUE INDEX ON iam.users (email)
  WHERE status != 'deleted';
```

- คอลัมน์เป็น `citext` อยู่แล้ว → `A@x.com` กับ `a@x.com` ชนกันเอง ไม่ต้องพันด้วย `lower()` ซ้ำ
- `WHERE status != 'deleted'` — อีเมลยังถูกจองไว้ตลอดช่วง grace period 30 วัน ไม่ให้คนอื่นแย่งไปสมัครแล้วเจ้าตัวกู้คืนไม่ได้ · หลัง anonymize แล้วอีเมลนั้นสมัครใหม่ได้ (เป็น account ใหม่คนละใบ)

## Organization

- Role ระดับ org: `owner` / `admin` / `member`
- ข้อมูลทุกอย่างผูกกับ org ผ่าน `org_id`
- **สร้าง org มี API แต่ยังไม่มีหน้าจอ** จนกว่าจะถึงเฟสหลัง — Phase 1-3 สร้างผ่าน API เท่านั้น

### หนึ่งคนอยู่ได้หลาย org ตั้งแต่ Phase 1

คนหนึ่งคนมีงานประจำ + งานนอก = อย่างน้อยสอง org และอาจเป็น **เจ้าของ** org ตัวเอง
แปลว่าข้อมูลของนายจ้างกับงานส่วนตัวอยู่ในฐานข้อมูลเดียวกัน คนละเจ้าของ

> cross-org isolation จึงไม่ใช่ของเผื่ออนาคต — **[RLS ที่วางไว้ Phase 2 ห้ามเลื่อน](./phase-2.md)**
> และ policy ต้องเป็น "org ที่ฉันเป็นสมาชิก" ไม่ใช่ "org ที่กำลังเปิดอยู่" ไม่งั้นหน้า Home จะว่าง

- **Org switcher** อยู่บนสุดของ sidebar · สลับแล้วทุกอย่างในหน้าเปลี่ยนตาม
- **หน้า Home** เป็นปลายทางหลัง login ไม่ใช่ project ใด project หนึ่ง — ตัวเลขสรุป ·
  งานใกล้ครบกำหนดข้าม org · รายชื่อ org ที่เป็นสมาชิก
- คนที่ยังไม่ได้อยู่ org ไหนเลย login ได้ แต่เห็นหน้าที่บอกให้ติดต่อ admin
  · **คำเชิญให้กดรับเป็นของ Phase 2** — หน้านี้ติดป้ายบอกไว้
  · ปุ่ม "สร้าง organization" **วาดไว้แล้วแต่ยังไม่ต่อหลังบ้าน** — กดแล้วขึ้นจอที่บอกว่า
    ถึง Phase 3 การสร้าง org ทำผ่าน admin API หรือ seed script เท่านั้น
    · วาดไว้เพื่อให้ตกลงรูปร่างกันไว้ก่อน ไม่ใช่เพราะเปลี่ยนใจเรื่องเฟส

**Owner มีได้หลายคน** (โมเดลแบบ GitHub) — ไม่ใช่ Primary Owner คนเดียวแบบ Slack

- ห้ามลบหรือลดสิทธิ์ **owner คนสุดท้าย** — org ต้องมี owner อย่างน้อย 1 คนเสมอ
- Owner ทำได้ทุกอย่างที่ admin ทำ + ลบ org + แต่งตั้ง owner คนอื่น
- UI แนะนำให้มี owner อย่างน้อย 2 คน

> เลือกโมเดลนี้เพราะปัญหา "owner หายไปแล้วไม่มีใครแก้อะไรได้" หายไปเองโดยไม่ต้องมี recovery flow หรือคนกลาง — ตอนใช้ภายในไม่มี support มารับเรื่องอยู่แล้ว
>
> GitHub แนะนำตรงๆ ว่าถ้ามี owner คนเดียว org อาจเข้าถึงไม่ได้ถ้าคนนั้นติดต่อไม่ได้

**ตาราง `organization.invitations` ลงตั้งแต่ Phase 1 แต่ยังไม่มีใครอ่าน** — API กับหน้าจอมา
[Phase 2](./phase-2.md) · Phase 1 เพิ่มคนเข้า org ด้วย seed script

## User States — Three Different Things

|                    | ใครกด       | เข้าระบบได้         | ยังอยู่ในรายชื่อ org   | ชื่อในงานเก่า     | Phase |
| ------------------ | ----------- | ----------------- | ----------------- | -------------- | ----- |
| **Deactivate**     | admin/owner | ✗                 | ✓ (ขึ้นว่า inactive) | ✓              | 1     |
| **Remove จาก org** | admin/owner | ✓ (แต่ไม่เห็น org นี้) | ✗                 | ✓              | 2     |
| **Delete account** | เจ้าตัวเท่านั้น  | ✗                 | ✗                 | ✓ ("ผู้ใช้ที่ถูกลบ") | 2     |

**ตัวอย่าง**

- พนักงานลาออก → **deactivate** (ยังเห็นชื่อในรายชื่อว่าเคยอยู่ กลับมาทำงานก็เปิดใหม่ได้)
- ฟรีแลนซ์จบสัญญา → **remove จาก org** (account เขายังใช้กับลูกค้าเจ้าอื่นได้ปกติ)
- ขอลบข้อมูลตาม PDPA → **delete account**

**Deactivate (Phase 1)**

- Assign งานใหม่ให้ไม่ได้
- **งานที่ค้างอยู่กับเขาอยู่เหมือนเดิม ไม่ย้ายไปไหน** — การปิดบัญชีคนไม่ใช่การมอบหมายงานใหม่
  ซึ่งเป็นการตัดสินใจที่ต้องมีคนทำ · หน้า Members เตือนว่าเขายังถืองานค้างอยู่กี่ใบ
- ถามว่า "งานของคนที่ inactive อยู่ไหนบ้าง" ด้วย filter assignee ธรรมดาได้ ไม่ต้องมี filter เฉพาะ
  · การโอนงานทั้งชุดทีเดียวคือ [Handover mode](./phase-4.md#handover-mode) ใน Phase 4
- Reactivate ได้

## Project

- สร้าง / แก้ไข / ลบ project
- **ชื่อ · สี · key prefix** — สีเป็น token จาก palette 8 สี ไม่ใช่ hex (ทรงเดียวกับ status)
- Project member เข้าได้อิสระ ไม่ผูกกับทีม (แบบ Slack channel)
- **Archive** — `archived_at` ซ่อนจาก sidebar และจาก picker ตอนสร้างงาน แต่ไม่ใช่การลบ
  สมาชิกยังเปิดดูประวัติได้ · งานข้างในไม่โผล่ใน My Tasks

**สร้าง project ได้เฉพาะ org owner / admin** — member สร้างไม่ได้

> ที่ ~100 คน 4 project การให้ทุกคนสร้างได้แปลว่า project งอกโดยไม่มีใครเก็บกวาด
> · เข้าชุดกับกติกาข้างล่างที่ member เห็นเฉพาะ project ที่ตัวเองเป็นสมาชิก —
> คนที่มองไม่เห็นภาพรวมว่ามีอะไรอยู่แล้วบ้าง ไม่ใช่คนที่ควรตัดสินว่าต้องมีอันใหม่

### สิทธิ์ระดับ project กั้นจริงตั้งแต่ Phase 1

- **member เห็นเฉพาะ project ที่ตัวเองเป็นสมาชิก**
- **owner / admin ของ org เห็นทุก project ใน org นั้น** — กันเคส project ที่สมาชิกลาออกหมด
  แล้วไม่มีใครเข้าถึงได้อีกเลย
- assign คนที่ยังไม่อยู่ใน project ได้ — ระบบถามยืนยันแล้วเพิ่มเข้า project ให้ ได้สิทธิ์ `member`
- role ระดับ project มี `admin` / `member`

> ไม่ใช่แค่ซ่อนใน UI — เป็นการกั้นที่ query · ถ้ากั้นแค่ที่ sidebar คนที่รู้ URL ก็ยังเปิดเข้าไปได้

## Task Key

`PREFIX-เลข` เช่น `DEV-120` — **prefix เก็บบน project เลขเก็บบน task ประกอบตอนแสดงผล**

- บังคับกรอกตอนสร้าง project · ตัวพิมพ์ใหญ่ · `^[A-Z][A-Z0-9]{1,5}$`
- เปลี่ยน prefix แล้ว key เปลี่ยนทั้ง project ทันที ไม่ต้อง backfill และไม่เก็บ prefix เก่า
- **prefix ซ้ำกันได้ในหนึ่ง org** — ผู้ใช้กรอกเอง ยอมรับว่า `TF-120` ชี้ได้สองงาน
  (ลิสต์แสดงชื่อ project ข้างเลขอยู่แล้ว · ค้นหาคืนหลายผลให้เลือก)
- เลขเริ่มที่ 1 ต่อ project · **sub-task มีเลขของตัวเอง** ไม่ใช่ `120.1`
- **ห้ามย้าย task ข้าม project** — เลขจะชนกับของเดิมและ key เก่าจะชี้ผิดงาน

> 🔒 เลขที่แจกไปแล้ว **ห้ามถูกแจกซ้ำ** แม้งานนั้นถูกลบ — คนแปะ `DEV-87` ไว้ในแชท
> วันหนึ่งเลขนั้นไปโผล่บนงานคนละใบคือความเสียหายที่ย้อนไม่ได้
> ([กลไกที่บังคับ](../02-database/schema.md#schema-task))

## Status (Custom Per Project)

กำหนดชื่อ, สี, ลำดับได้เอง — สีเลือกจาก palette 8 สี เก็บเป็น **token ไม่ใช่ hex**

| Token    | ใช้สื่อ                | Tailwind (light) |
| -------- | ------------------- | ---------------- |
| `gray`   | ยังไม่เริ่ม / พัก        | slate-500        |
| `red`    | ติดปัญหา / blocked    | red-500          |
| `orange` | เร่งด่วน / รอแก้       | orange-500       |
| `yellow` | รอตรวจ / รอ approve | amber-500        |
| `green`  | เสร็จ / ผ่าน          | emerald-500      |
| `blue`   | กำลังทำ              | blue-500         |
| `purple` | รอคนอื่น / external   | violet-500       |
| `pink`   | อื่นๆ                 | pink-500         |

**Default ตอนสร้าง project ใหม่** — hardcode ในโค้ด ไม่มีชุดกลางระดับ org ให้ตั้งค่า

| ชื่อ          | สี     | is_default | ประเภท    |
| ----------- | ----- | ---------- | --------- |
| To do       | gray  | ✅         | —         |
| In progress | blue  | —          | —         |
| Done        | green | —          | เสร็จ      |
| Cancelled   | pink  | —          | ยกเลิก     |

> มี Cancelled ในชุดตั้งต้นเพราะ project ที่ไม่มี status ประเภท "ยกเลิก" จะไม่มีที่ให้ทิ้งงาน
> ที่ตัดสินใจไม่ทำ คนจะเอาไปกอง Done แทน แล้ว progress กับ velocity เพี้ยนทั้งคู่

**กติกา**

- 1 project มี `is_default` ได้แค่ 1 อัน (status ตั้งต้นของ task ใหม่)
- 1 project ต้องมี `is_done_type` อย่างน้อย 1 อัน
- `is_cancelled_type` — "ยกเลิก/ไม่ทำแล้ว" ไม่ใช่ "เสร็จ" (ใช้ตอนคำนวณ progress)
- status หนึ่งอันเป็นได้ทั้ง done และ cancelled ไม่ได้ — เลือกอย่างใดอย่างหนึ่งหรือไม่เป็นเลย
- ห้ามลบ status ที่ยังมี task ใช้อยู่ / ห้ามลบอันสุดท้าย
- `completed_at` / `completed_by` ต้องมีค่า **ก็ต่อเมื่อ** status ของ task นั้น `is_done_type` — บังคับที่ application เพราะเงื่อนไขข้ามตาราง (`tasks` ↔ `statuses`) ซึ่ง `CHECK` ทำไม่ได้ · ต้องคุม**สองทาง** ไม่ใช่ทางเดียว: ตอน task เปลี่ยน status (ข้อบน) และตอนมีคนแก้ `is_done_type` ของ status ที่มี task ใช้อยู่แล้ว — ทางหลังลืมง่ายกว่า เพราะคนแก้กำลังมองหน้าจอตั้งค่า project ไม่ได้มองงานสักใบ
- แสดงเป็น badge สีอ่อน + ตัวอักษรเข้ม **พร้อมชื่อเสมอ** (คนตาบอดสี ~8% ของผู้ชาย)

**หน้าจอแก้ status อยู่ใน Project settings** — ไม่ใช่แค่กติกาในสเปก ต้องมีที่ให้กด

- รายการ status เรียงลำดับได้ · แต่ละแถวมี ชื่อ · สี · ประเภท (ปกติ / เสร็จ / ยกเลิก) · ปุ่มลบ
- ปุ่มลบของ status ที่ยังมีงานใช้อยู่เป็นสีจาง + tooltip บอกจำนวนงาน — ไม่ใช่กดแล้วขึ้น error
- เครื่องหมายระบุ status ตั้งต้น เลือกได้อันเดียว

```
project.statuses
  name
  color               -- token จาก palette 8 สี ไม่ใช่ hex
  sort_order          -- fractional indexing
  is_default          -- status ตั้งต้นของ task ใหม่
  is_done_type        -- นับเป็น "เสร็จ"
  is_cancelled_type   -- นับเป็น "ยกเลิก" — ตัดออกจากตัวหารของ progress
```

- **Priority มีสี่ระดับ** — `urgent` / `high` / `medium` / `low` (ว่างได้)
- **Quick add** — พิมพ์ชื่องาน + Enter จบ ไม่บังคับ field อื่น
  **เฉพาะในหน้า project** ที่รู้อยู่แล้วว่างานจะไปลงที่ไหน
- Status จาก custom status ของ project
- **Assign ได้หลายคน** (เฉพาะ user — ทีมอยู่ Phase 2)
- จัดลำดับเอง (fractional indexing)
- แสดง "เสร็จโดยใคร เมื่อไหร่" (`completed_by`, `completed_at`)
- **เปลี่ยนสถานะกลับจาก done → ไม่ done → `completed_by` / `completed_at` reset เป็น null** ปิดใหม่อีกครั้งก็บันทึกค่าใหม่ (ประวัติการปิด-เปิดอยู่ใน activity log อยู่แล้ว)

> **My Tasks ไม่มี quick add** — มันไม่ได้อยู่ใน project ไหน จะพิมพ์ชื่องานแล้วจบไม่ได้
> ต้องเลือก project ก่อนเสมอ ซึ่งเพิ่มแรงเสียดทานที่ quick add มีไว้ลดพอดี
>
> ถ้าจะเพิ่มทีหลังจริงๆ ใช้ `localStorage` จำ project ล่าสุด **ไม่ต้องมีตาราง user preference**

**Assignee picker** (สำคัญเมื่อบริษัทมีคน 100+)

- Type-ahead ค้นได้ทั้งชื่อจริง / ชื่อเล่น / อีเมล — ไม่ใช้ dropdown รายชื่อยาว
- **เรียงสองชั้นพอ:** คนใน project นี้ก่อน แล้วปุ่ม "ค้นหาทั้งองค์กร"
- เลือกคนนอก project → ถามว่าเพิ่มเข้า project เลยไหม
- แสดง avatar + ชื่อ + ชื่อเล่น ในแต่ละแถว (กันเลือกผิดคน)
- Keyboard navigation: ลูกศร + Enter

> เดิมมีชั้นกลาง "คนที่เพิ่ง assign ไปล่าสุด" คำนวณจาก activity log — **ตัดออก** เพราะเป็น query
> ที่แพงที่สุดในหน้าจอที่เปิดบ่อยที่สุด เพื่อจัดลำดับที่คนใน project ตอบได้อยู่แล้วเกือบทุกครั้ง
> · ถ้าวันหนึ่ง project ใหญ่จนลิสต์ยาวเกินไป ค่อยกลับมาคิด ตอนนั้นจะมีข้อมูลจริงให้ดู

## Views

- **List view** — รับ config คอลัมน์เป็น array จากที่เดียว (hard-code ไว้ก่อนได้) ไม่เขียน `<th>` ตายตัวใน JSX เพื่อให้ต่อ `view.columns` ใน Phase 4 ได้โดยแก้จุดเดียว
- **Filter · sort · group by · search** ครบตั้งแต่ Phase 1
- **การเรียงไม่ทำให้ต้นไม้แบน** — เรียง parent ก่อน แล้วเรียงลูกภายใต้ parent ของตัวเอง
  ไม่ใช่เรียงทุกแถวปนกัน · sub-task ที่ลอยไปอยู่คนละที่กับพ่อทำให้ list อ่านไม่รู้เรื่อง
  (มีผลตั้งแต่ Phase 2 ที่ sub-task มีจริง แต่เขียนกติกาไว้ตอนเขียน query รอบแรก)
- **เงื่อนไข filter ทุกข้อต้องเป็นจริงพร้อมกัน (AND)** — ไม่มี OR ระหว่างข้อ
  · ต้องการหลายค่าในข้อเดียวใช้ "is in" ที่รับหลายค่า
- **เก็บสถานะไว้ใน URL ไม่ใช่ save เป็น view** — view ที่ save ได้เป็นของ Phase 4
  URL ทำให้ส่งลิงก์ให้เพื่อนแล้วเห็นเหมือนกันได้ทันที โดยไม่ต้องมีตารางอะไรรองรับ
- Filter: คน, status, priority, วันที่, sprint (เมื่อเปิดใช้)
- **My Tasks** — งานที่ assign ให้ตัวเอง (ยังไม่มีทีม)
  **ค่าเริ่มต้นซ่อน status ที่เป็น done และ cancelled** — เปิดมาเจอสิ่งที่ต้องทำ ไม่ใช่กองงานที่ทำไปแล้ว
  ผู้ใช้ปรับ filter เองได้ตั้งแต่ Phase 1 แต่ยังจำค่าไม่ได้ (การจำมาพร้อม view ส่วนตัวใน Phase 4)

## Notifications

- ส่งอีเมลเมื่อถูก assign งาน — **แค่อย่างเดียวใน Phase 1**

> ถ้าไม่มีแจ้งเตือนเลย คนจะไม่รู้ว่ามีงานมอบหมายมา แล้วจะไม่กลับเข้าระบบ
>
> แจ้งเตือนชนิดอื่นและ **กล่องขาเข้าในเว็บ (Inbox)** อยู่ [Phase 3](./phase-3.md) — Phase 1 ยังไม่มี
> `notify.notifications` และหน้าจอไม่ควรมีกระดิ่ง

**Provider: Resend** — API สะอาด, ฟรี 3,000 ฉบับ/เดือน, ตั้ง domain ง่าย, ใช้ React Email เขียน template ในโค้ดเดียวกันได้

ห่อด้วย **`EmailService`** เหมือน `StorageService` — เปลี่ยน provider ทีหลังแก้จุดเดียว (ทางเลือกสำรอง: SES ถูกกว่าถ้าส่งเยอะ, Brevo, SMTP ของ Bangmod)

**Outbox pattern** (ใช้ `notify.outbox`)

```
1. บันทึกลง outbox ใน transaction เดียวกับ business logic
2. Worker อ่านแถวที่ยังไม่ส่ง → ส่ง → mark sent
3. ส่งไม่สำเร็จ → retry 3 ครั้ง (exponential backoff)
4. ครบ 3 ครั้ง → mark failed + แจ้ง Sentry
```

> ถ้าส่งอีเมลตรงใน request แล้ว provider ล่ม จะเสียทั้ง transaction หรือ assign สำเร็จแต่ไม่มีใครรู้
