# Phase 3 — ทำงานร่วมกัน `v1.2.0`

> [← Feature Specifications](./README.md) · [ลำดับและ priority](../03-roadmap.md)

**นี่คือเฟสที่ปล่อยให้คนใช้จริง** — Phase 1-2 สร้างแกน Phase 3 ทำให้มันเป็นที่ที่คนอยากกลับมา
· ของที่ปล่อยผ่านได้เพราะ "เดี๋ยวค่อยทำ" หมดข้ออ้างตรงนี้ เพราะไม่มีเฟสถัดไปก่อนคนใช้แล้ว

จบเฟสนี้หน้าตาจะเท่ากับ design ที่วาดไว้ ยกเว้นสามอย่างที่อยู่นอกกรอบตั้งแต่แรก —

org settings ส่วน logo / timezone / ค่าเริ่มต้น

## Kanban Board

drag & drop ([`sort_order` แบบ LexoRank](../01-architecture.md#lexorank--sort_order) ได้ใช้จริงตรงนี้) · จัดกลุ่มตาม status ของ project

**Sub-task แสดงเป็นการ์ดแยก** พร้อมตัวบอกว่าเป็นลูกของใคร

```
┌─────────────────────┐
│ ↳ ออกแบบ mockup      │
│   จาก: ทำหน้า login   │
│   👤 สมชาย            │
└─────────────────────┘
```

เหตุผล: Kanban คือเครื่องมือติดตาม flow ของงาน ถ้าซ่อน sub-task คนที่ถูก assign จะไม่เห็นงานตัวเองบน board
(ต่างจาก List view ที่ใช้ `WHERE depth = 0` เพราะแสดงแบบ indent อยู่แล้ว)

มี toggle "ซ่อนงานย่อย" สำหรับ PM ที่อยากดูภาพรวมระดับบน

- คอลัมน์เรียงตาม `statuses.sort_order` เดียวกับที่หน้า settings จัด
- ลากข้ามคอลัมน์ = เปลี่ยน status → ลง activity log เหมือนการแก้จากที่อื่นทุกประการ
- status ที่ `is_done_type` ทำให้ `completed_at` / `completed_by` ถูกตั้ง — กติกาเดียวกับ Phase 1
  ไม่ใช่ทางลัดของ board

## Comment + Thread

`discussion.comments` — [ดู schema เต็ม](../02-database/schema.md#schema-discussion)

- **thread ชั้นเดียวแบบ Slack** — `parent_comment_id` ชี้ที่ **comment ต้นเธรด** เสมอ
  ไม่ใช่ชี้ต่อกันเป็นลูกโซ่ · ตอบกลับคำตอบก็ยังอยู่เธรดเดิม ไม่มีการเยื้องซ้อนไม่รู้จบ
- `entity_type` / `entity_id` เป็น polymorphic ไม่มี FK (ทรงเดียวกับ `audit.logs`) —
  Phase 3 ใช้กับ task อย่างเดียว แต่ไม่ต้องแก้ตารางตอนอยากคอมเมนต์ของอย่างอื่น
- แก้ไขได้ → `edited_at` ไม่ null แล้วแสดงป้าย "แก้ไขแล้ว" ข้างเวลา
- **ลบ comment ที่มีคนตอบแล้ว = แสดง "ความคิดเห็นถูกลบ" ไม่ใช่หายไปทั้งเธรด** —
  เธรดที่หัวหายคือบทสนทนาที่อ่านไม่รู้เรื่อง
- **@mention ได้เฉพาะสมาชิก project** — ถ้า mention คนนอกให้เสนอเพิ่มเข้า project ก่อน
  (ทรงเดียวกับตอน assign คนนอก) ไม่ใช่เงียบๆ แล้วเขาไม่ได้รับแจ้งเตือน

> design รวม comment กับ activity log ไว้ในแท็บเดียวกัน ("Comments & activity") ในหน้า drawer
> — คนอ่านคำถามเดียวกันว่า "งานนี้เกิดอะไรขึ้นบ้าง" ไม่ได้แยกในหัวว่าอันไหนคนพิมพ์อันไหนระบบบันทึก

## Inbox + แจ้งเตือนครบชุด

🔴 **ข้อที่ห้ามตัดของเฟสนี้** — ระบบที่ไม่บอกว่ามีอะไรเกิดขึ้นกับงานของคุณ คือระบบที่คนเปิดครั้งเดียวแล้วไม่กลับมา
· Phase 1 มีแค่อีเมลตอนถูก assign ซึ่งพอสำหรับตอนที่ยังไม่มีใครใช้จริง แต่ไม่พอสำหรับตอนนี้

**ตารางใหม่ `notify.notifications`** — [ดู schema เต็ม + เหตุผลที่แยกจาก `outbox`](../02-database/schema.md#schema-notify)

| ชนิด | เกิดเมื่อ |
| --- | --- |
| `assigned` | ถูก assign (ตรงๆ หรือผ่านทีม) |
| `mentioned` | ถูก @ ใน comment |
| `comment` | มี comment ใหม่ในงานที่เราเกี่ยวข้อง |
| `status_changed` | สถานะงานที่เราถืออยู่เปลี่ยน |
| `due_soon` | ใกล้ถึงกำหนด — มาจาก cron ไม่ใช่จากการกระทำของใคร → `actor_id` เป็น null |
| `stale` | งานค้างเกินเกณฑ์ ([ดูข้างล่าง](#stale-detection)) |

**กติกา**

- **แถว notification เขียนใน transaction เดียวกับการกระทำ** ไม่ใช่ผ่าน event emitter —
  เหตุผลเดียวกับ [audit](../01-architecture.md#how-the-activity-log-is-written): listener ที่พังทำให้
  "assign แล้วไม่มีแจ้งเตือน" เกิดโดยไม่มี error ที่ไหน · ส่วนการ**ส่งออก**ทางอีเมล/แชท
  ยังเดินผ่าน `notify.outbox` ตามเดิม เพราะนั่นคุยกับของนอกระบบและต้อง retry ได้
- **ไม่แจ้งเตือนคนที่เป็นคนทำเอง** — `actor_id = recipient_id` แล้วข้าม · จุดที่พลาดง่ายที่สุด
  และเป็นเหตุผลอันดับหนึ่งที่คนปิดแจ้งเตือน
- **ตัวเลข unread แยกตาม org** — index มี `org_id` นำอยู่แล้ว สลับ org แล้วตัวเลขเปลี่ยน
  ถูกต้องแล้ว ไม่ใช่บั๊ก
- อ่านแล้ว = `read_at` · มีปุ่ม "อ่านทั้งหมด" · ไม่ลบแถว ปล่อยให้ retention จัดการ
- Inbox เป็นหน้า/แผงในเว็บ + กระดิ่งพร้อมตัวนับ — Phase 1 ตั้งใจไม่มีกระดิ่ง เพราะกดแล้วไม่มีอะไร

## ไฟล์แนบ

`discussion.attachments` + object storage (Garage) — [ดู schema เต็ม](../02-database/schema.md#schema-discussion)

- **bucket เป็น private เข้าถึงผ่าน presigned URL เท่านั้น** ไม่มี URL ถาวรที่แชร์ต่อได้ตลอดกาล
- ตรวจขนาดและชนิดไฟล์**ที่ API** ไม่ใช่แค่ที่เบราว์เซอร์ · เพดานขนาดเก็บเป็น env var
- ไฟล์อยู่คนละที่กับฐานข้อมูล → **backup แยกกัน** และกู้คืนแยกกัน (`deploy/backup.sh` แยกไดเรกทอรีให้อยู่แล้ว)
- ลบ task → แถว attachment ถูก soft delete ไปด้วย ส่วน object ในสตอเรจให้ retention job
  ตามลบทีหลัง — ลบทันทีแล้วกู้ task กลับมาจะได้แถวที่ชี้ไปยังไฟล์ที่ไม่มีอยู่
- ตารางมีมาตั้งแต่ Phase 0 และอยู่ใน `AGGREGATE_CHILDREN` แล้ว (ใต้ `task.tasks`) —
  ลบงานแล้วไฟล์แนบตามไปเอง ไม่ต้องเพิ่มอะไร

## Sprint Board + Carry Over

**Sprint board** — Kanban ที่ filter ด้วย sprint (ไม่ต้องเขียน view ใหม่) · แสดง sub-task เหมือน Kanban ปกติ และใช้ toggle "ซ่อนงานย่อย" ตัวเดียวกัน

**ปิด sprint + carry over** — ตอนปิด sprint ระบบถามว่างานที่ยังไม่ `is_done_type` จะเอาไปไหน:

- ย้ายไป sprint ถัดไป (default)
- เอากลับ backlog (`sprint_id = null`)
- ปิดทิ้ง → เปลี่ยนเป็น status ที่เป็น `is_cancelled_type` (ไม่ใช่ `is_done_type`) เพราะไม่ได้ทำจริง — มีผลกับ velocity ใน Phase 4

ห้ามย้ายอัตโนมัติเงียบๆ · บันทึกลง activity log ว่า task carry over มากี่รอบแล้ว — ข้อมูลนี้มีค่ามากตอนรีวิว

> Phase 2 ปิด sprint แบบง่าย (ตกไป Backlog อย่างเดียว) ไปแล้ว — ข้อนี้คือการเพิ่มตัวเลือก
> ไม่ใช่การทำใหม่

## Filter ของ My Tasks ปรับเอง

Phase 1 ให้ My Tasks ซ่อน done/cancelled เป็นค่าเริ่มต้นแบบตายตัว · Phase 3 ให้ผู้ใช้ปรับเอง

- filter ได้ตาม: project (**รวม project ที่ archive แล้ว**) · status · sprint · ทีม · ซ่อน/แสดง done+cancelled
- **เก็บใน URL เหมือนหน้า project** ไม่ได้ save เป็น view — view ที่ตั้งชื่อและใช้ซ้ำได้เป็นของ [Phase 4](./phase-4.md)

> **นี่คือทางเดียวที่จะเห็นงานใน project ที่ archive ไปแล้ว** ([archive ทำอะไรบ้าง](./phase-2.md#archive-project))
> — ระหว่าง Phase 2 ถึง Phase 3 การ archive แปลว่างานหายจาก My Tasks จริงๆ

## Activity Feed ระดับ Project

แท็บที่สามในหน้า project ต่อจาก List / Board · Phase 2 ทำรายการในหน้า task ไปแล้ว
ข้อนี้คือการตอบคำถาม _"project นี้เกิดอะไรบ้าง"_ ซึ่งเป็นคนละหน่วยของคำถาม
([ตารางใครเห็นอะไร](./phase-2.md#activity-log-บนหน้า-task))

- **filter 3 ตัว: คน · ชนิด event · ช่วงเวลา**
- **event ระดับบริหาร (เพิ่ม/ถอดคน, แก้ settings) เห็นเฉพาะ project admin และ org owner/admin**
  — สมาชิกธรรมดาเห็นเฉพาะ event ที่เกี่ยวกับงาน
- ไม่มีมุมมอง "คนนี้ทำอะไรบ้าง" — filter ตามคนได้**ภายใน project เดียว**เท่านั้น
  ไม่มีหน้าที่รวมกิจกรรมของคนคนหนึ่งข้าม project ([เหตุผล](./phase-2.md#activity-log-บนหน้า-task))

**feed นี้ query ยังไง — ตัดสินแล้ว 2026-09-03: ไม่เพิ่มคอลัมน์ลง `audit.logs`**

`audit.logs` ไม่มี `project_id` มีแต่ `entity_type` + `entity_id` แบบ polymorphic
· feed จึงประกอบจากสองส่วน:

| ส่วน | หามาจากไหน |
| --- | --- |
| event ระดับบริหาร (เพิ่ม/ถอดคน, แก้ settings) | `entity_type='project'` + `entity_id=<project id>` — **index ที่มีอยู่ตอบได้เลย** ไม่ต้องแก้อะไร |
| event ของงานใน project | ฝั่ง project หา task id ของตัวเองก่อน แล้วส่งเข้ามาเป็นลิสต์ |

**เหตุผลที่ไม่เพิ่ม `project_id` ทั้งที่ตอนนี้เพิ่มได้ฟรี** — `audit.logs` ตั้งใจให้ไม่รู้จัก
โดเมนของใครเลย ([ทำไม](../01-architecture.md#reading-the-audit-log-from-other-modules))
· `project_id` คือการสอนตารางนี้ให้รู้จักคำว่า project ซึ่งผิดทางกับกติกาที่คุมมันอยู่ ·
ทางที่เลือกเข้ารูปเดิมพอดี: audit รับ **ลิสต์ของ entity id** แล้วคืน log ออกไป
โดยไม่ต้องรู้ว่ามันคืองานของ project ไหน — ทรงเดียวกับ `findRecentTargets`
ที่คืน id ออกไปให้ผู้เรียกตีความเอง

ต้นทุนจริงของคอลัมน์ไม่ใช่ migration แต่คือทุกจุดที่เขียน log ต้องจำเติมค่าให้ถูกตลอดไป
· **คอลัมน์ที่เติมพลาดเงียบๆ แย่กว่าไม่มีคอลัมน์** เพราะ feed จะขาดไปโดยไม่มีใครรู้

## Stale Detection

งานที่ไม่มีความเคลื่อนไหวเกินจำนวนวันที่ project ตั้งไว้ โผล่เป็นแถบเหนือรายการงาน

```
⚠ 3 งานค้างมาเกิน 7 วัน                              [ดูทั้งหมด] [ปิด]
```

- **เกณฑ์ตั้งเองต่อ project** — `project.projects.stale_after_days` · **null = ปิดฟีเจอร์**
  · ค่าที่ UI เสนอตอนเปิดคือ 7 · setting อยู่ในหน้า project settings
- **ทุกคนใน project เห็นเท่ากัน** ไม่ใช่แค่ admin และไม่ใช่แค่เจ้าของงาน — งานหลุดเรดาร์
  เป็นปัญหาของทีม ไม่ใช่ความผิดของคนที่ชื่อติดอยู่
- อยู่ใน**หน้า project** เหนือรายการงาน เห็นทั้งแท็บ List และ Board
- **ไม่อยู่บนหน้า home** — home เป็นหน้าส่วนตัวข้าม org วางตรงนั้นแล้วฟีเจอร์จะกลายเป็น
  "งานของฉันที่ค้าง" ซึ่งเตือนคนที่รู้อยู่แล้วว่าตัวเองไม่ได้ขยับงาน
- ปิดแถบได้ต่อ project (จำที่ฝั่ง client) · ไม่ปิดถาวรให้ทั้งทีม
- ใช้ `audit.logs` ที่เก็บมาตั้งแต่ Phase 0 — **ไม่ต้องใช้ AI เลย**
- ต่างจากเตือน deadline ทั่วไปตรงที่**จับปัญหาก่อนถึง deadline**

> 🔒 **ห้ามมีค่าเฉลี่ย ห้ามมียอดรวมรายคน — ทุกที่ รวมทั้งใน tooltip**
>
> แถบนี้ทุกคนใน project เห็น การเขียนว่า _"งานปกติของทีมนี้ใช้เวลา 3 วัน"_ คือการเอาสมาชิก
> ไปเทียบกับค่ากลางต่อหน้าคนทั้ง project เพราะงานค้างมีชื่อ assignee ติดอยู่ทุกแถว ·
> เป็นสิ่งเดียวกับที่ปฏิเสธไปแล้วสองที่: [leaderboard รายคน](./phase-4.md#estimate--velocity)
> และคำถาม ["คนนี้ทำอะไรบ้าง"](./phase-2.md#activity-log-บนหน้า-task) → **ไม่ทำ**
>
> _(สเปกเดิมของข้อนี้เขียนว่า "เทียบกับพฤติกรรมจริงของทีมนั้น ไม่ใช่กฎตายตัว" — ยกเลิกทั้งก้อน
> เมื่อ 2026-09-03 · ที่ยอมเสียคือความเป็นของที่ลอกยาก ที่เหลือคือ "งานไม่ขยับเกิน N วัน"
> ซึ่งเครื่องมืออื่นก็มี แต่ประโยชน์จริงยังอยู่ครบ)_
